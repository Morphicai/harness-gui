# 宿主与调用方式

## 一、宿主是一等概念

`browser` / `native` / `electron` 是**同一份页面的三种承载**，不是三套实现。
页面、协议、表单逻辑只有一份（`channels/web`），宿主只决定它装在什么窗口里。

| 宿主 | 状态 | 换来什么 | 代价 |
|---|---|---|---|
| **browser** | ✅ | 零安装、跨平台、无需分发 | 无系统通知、无常驻、关标签页即失联 |
| **native**（Zig） | ✅ macOS | 系统通知、状态栏常驻、关窗不退出；**很轻**（3–8 MB） | 每平台单独构建；**壳内跑不了 Node** |
| **electron** | 计划 | 上述全部 + **壳内可执行 Node** | 体积 ~150 MB+、每平台单独出包 |

electron 的独有价值只有一条：**壳自己能跑 Node**。交互界面里要直接执行本地逻辑
（读文件、调本地工具、跑一段脚本）时，不必把请求穿回调用方进程。
不需要这条的场景，native 更划算 —— 二十倍的体积差距不是小事。

## 二、Web 页面怎么调起本地

### 自定义 scheme 只负责一件事：冷启动

页面直连 `127.0.0.1` 有个死穴：**app 没在跑的时候连不上，而页面无法启动本机进程**。
自定义 scheme（`harness-gui://…`）补的正是这一格 —— 由操作系统把 app 叫起来。

所以两者是配合关系，不是替代：

```
页面                          本机
 │
 ├─① 先试 loopback ─────────► app 在跑？──是──► 直接用 HTTP/WS 通信
 │                                 │
 │                                否
 │                                 ▼
 ├─② location = harness-gui://wake?…  ──► OS 拉起 app
 │
 └─③ 退避重试 loopback ─────────────────► 通了，继续 ①
```

**数据不要走 scheme。** URL 会进浏览器历史、系统日志、崩溃报告，甚至 referrer；
把 token 或表单内容塞进 URL 等于到处留副本。scheme 里只放「醒来」+ 一个短时效的
一次性握手码，真正的往返走 loopback。

注册方式：macOS 在 `Info.plist` 的 `CFBundleURLTypes`；
Windows 在 `HKCU\Software\Classes\harness-gui`（免管理员权限，按用户注册）。

### 这条通路的安全代价必须先说清

**自定义 scheme 是任何网页都能触发的。** `evil.com` 上一个 `<a href="harness-gui://…">`
就能让本机弹窗。所以设计上必须站在「调用方完全不可信」的立场：

| 约束 | 为什么 |
|---|---|
| **scheme 输入一律视为敌意输入** | 它来自开放网络，不是来自我们的代码 |
| **来源必须显示在界面上，不是元数据** | 人要看到「`evil.com` 请求你确认删除 12 行」，而不是只看到「确认删除 12 行」。<br>provenance 是 UI 的一部分 |
| **首次接触需一次显式配对** | 人批准某个 origin 一次，本地记住。没有配对就只显示「未知来源请求接入」，<br>而不是直接把业务请求渲染出来 |
| **★ 调用方永远不能描述「要执行什么」** | 只能引用**本机已注册**的任务 id。<br>允许 URL 携带待执行的代码或命令 = 一条 URL 就是远程代码执行。<br>这条在 electron 宿主下尤其致命 —— 那边真有 Node |
| **一次性码短时效、单次使用** | URL 会留痕，必须假设它已经泄漏 |

一句话：**scheme 带进来的是「请求」，不是「指令」。** 模型和网页都能构造请求，
构造不出人的批准 —— 这与库本身的立场一致（见 README 第 3 条设计规则）。

## 三、远程智能体直接调用（更后面）

远程调用**不能走 scheme** —— scheme 只在本机有效。要让机房里的 agent 找到某个人，
连接方向必须反过来：

```
远程 agent ──► 中继（relay）◄── 本地 app 主动外连并保持
                   │
                   └─ 请求排队，本地 app 拉取 → 呈现给人 → 结果回传
```

**本地 app 主动外连**，而不是开入站端口。这样绕开 NAT / 防火墙 / 动态 IP，
也不必在用户机器上暴露监听面 —— 这是唯一现实可行的形态。

需要在中继形态里解决的：

- **设备配对**：一次性配对码把「某个远程 agent」和「某台设备上的某个人」绑起来
- **端到端**：中继只转发密文，看不到表单内容与批准结果（否则中继成了最高权限方）
- **请求归属**：人看到的是「哪个 agent、代表谁、要干什么」，不是一条匿名请求
- **限流与静音**：远程方无法靠刷请求把人淹没；人能一键静音某个 agent

## 四、落地顺序

1. **browser / native 平级化**（表述与包结构）—— 现在读起来像「native 才是正路」
2. **scheme 冷启动**：wake + 一次性握手码 + origin 配对 + 界面显示来源
3. **electron 宿主**：仅在确实需要「壳内跑 Node」时；先明确它比 native 多解决什么
4. **远程中继**：配对 + 端到端 + 归属显示，独立设计评审后再动手

前两步在现有架构里是加法；后两步各自带一套分发与信任问题，不要混在一起做。
